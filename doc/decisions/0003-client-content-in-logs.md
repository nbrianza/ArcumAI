# ADR 0003: Client content in logs

- Status: accepted (owner approval on issue #39, decisions D1a to D1e)
- Date: 2026-10-24
- Issue: #39

## Context

The server log (`logs/server.log`, rotated daily and kept 30 days) and the add-in log (`plugin.log`, `plugin.log.old`) recorded email subjects and bodies, optimized prompts, search and chat queries, attachment and upload file names, and exception text that can quote them. Logs are copied into support sessions and backups far more freely than the archive, so they were the easiest path for client data to leave the office.

The owner also wants a way to see full details while developing.

## Decision

Default logs never contain client content (subject, body, prompt, query, answer, file name, or exception text that can quote them). They carry ids (user, Outlook id, request id), counts, sizes, durations and sanitized extensions (`safe_ext` on the server, `SafeExt` in the add-in: the lower-cased suffix if it is 1 to 8 alphanumeric characters, otherwise `other`).

Client content may be logged only through `src.logger.content()` (server) or `PluginConfig.Content()` (add-in). They return it only when `LOG_CLIENT_CONTENT=true` together with `ARCUMAI_ENV=dev` (server; the server refuses to start with the switch on outside dev) or `LogClientContent=true` in the local add-in configuration. When on, the value is written on one line (newlines escaped). The switch is never pushed by the server. Startup logs a WARNING while it is on. Logs written while it is on must be purged after use.

One request id, generated by the add-in and used as the JSON-RPC id, correlates an email across `server.log` (`req=...`) and `plugin.log` (`ID: ...`).

## Alternatives considered

- A logging filter or formatter that redacts patterns: content has no recognisable pattern, so redaction would be partial.
- Moving content lines to DEBUG only: DEBUG is often enabled during support sessions.
- A truncated hash of the subject: unnecessary with the request id, and reversible for low-entropy subjects.
- A separate content log file: its own rotation and retention, one more place to forget.
- Pushing the add-in switch from the server at `client/identify`: one server setting would turn on content logging on every user PC without the user knowing, and the cached value would stay applied before the server is reachable.

## Consequences

- Support searches logs by request id, not by subject. The web chat log line no longer shows the start of the question.
- Every new log line that touches client data must go through `content()` or `PluginConfig.Content()`; static guards in `tests/test_log_privacy.py` fail otherwise.
- Exception text and tracebacks can quote client input, so the bridge, loopback, session, NER masking, prompt optimizer and add-in error lines log only the exception type by default (plus HResult in the add-in); text and traceback only with the switch on. This reduces the default diagnostic detail of error logs.
- `ingestion.log` (ingest, watcher, readers) still logs archive file names; it is out of scope here and tracked as a follow-up (decision D4).
- If `ARCUMAI_ENV=dev` gains other effects, the coupling with `LOG_CLIENT_CONTENT` must be revisited.
